Status: **release verification recorded; not a legal opinion**.

The scope is the Lyrion plugin and native Bliss repositories reviewed from 2026-10-31. Previously published development snapshots remain outside this task.

### Supplemental-notice provenance check

- `convert_case` 0.4.0 declares MIT and records upstream commit `300d9eef9e8c970e15f324afbc3df8b6a4ebbf71`. The included [MIT text](https://github.com/rutrum/convert-case/blob/f72ca63c9d579fbab22e361c76e39d31d1e86a2e/LICENSE) was added by the author two commits later on 2020-05-25. This supports the selected notice but is not a license file present at the recorded crate commit.
- `kernel32-sys` 0.2.2's published source identifies Peter Atashian, 2015, and MIT; the included [historical upstream MIT text](https://github.com/retep998/winapi-rs/blob/0d92b96a117f263d59d3121eafbc8a7051c3c49e/LICENSE.md) matches that attribution. Related legacy WinAPI crates remain subject to their own source-header and target checks.
- `fuchsia-zircon-sys` 0.3.3 was published on 2018-01-05 according to [crates.io metadata](https://crates.io/api/v1/crates/fuchsia-zircon-sys/0.3.3), declares BSD-3-Clause and its source credits the 2016 Fuchsia Authors but references a missing LICENSE. The supplied [historical upstream BSD-style text](https://fuchsia.googlesource.com/garnet/+/436615b7943b65378e130b189d0992429d1fb7c8/LICENSE) credits 2017 and was taken from a 2019-01-25 commit; its applicability to the exact crate revision is not independently established. It remains in the distributed source snapshot. For mixer v0.11.6, `cargo tree --locked --edges normal,build` for its six actual release targets did not list this crate; that is a dependency-tree observation, not a legal conclusion about source redistribution.
  - Further corroboration: [Debian's copyright record for 0.3.3-2](https://metadata.ftp-master.debian.org/changelogs/main/r/rust-fuchsia-zircon-sys/rust-fuchsia-zircon-sys_0.3.3-2_copyright) identifies BSD-3-Clause and the Fuchsia Authors for 2016–2018. An independent [third-party notice explicitly naming 0.3.3](https://dc.circularprotocol.live/licenses) reproduces a 2016 Fuchsia Authors BSD-style notice. These are useful secondary evidence, not the missing exact-revision upstream license; Debian's third clause also uses different wording from the supplied upstream text. Do not silently replace the supplement or treat this as definitive provenance.
  - A closer primary source is the published [parent crate `fuchsia-zircon` 0.3.3](https://crates.io/api/v1/crates/fuchsia-zircon/0.3.3/download): its original manifest declares `fuchsia-zircon-sys` 0.3.3 as a path dependency, and its included LICENSE credits the 2016 Fuchsia Authors. That exact license text has now been added to the version-specific supplement in mixer commit `41e9f34` alongside the previously recorded 2017 upstream text. A regression test verifies its SHA-256 (`f82f9062a6dff28145c185f90f94c485eebdc2bb4c6f1c840513709e6d228453`). This supports provenance but does not independently identify the exact original upstream revision of the sys crate.
- `actix-macros` 0.1.3 declares `MIT OR Apache-2.0`, but its two published license files contain only relative paths. Mixer v0.11.6's notice bundle does contain byte-identical copies of the [upstream MIT text at the crate's recorded commit](https://github.com/actix/actix-net/blob/ab496a71b576b29a9fd07064c11eda55428fb552/LICENSE-MIT) under other Actix crates, but does not explicitly associate one with `actix-macros`. The original presence check missed this. A specifically labelled supplemental MIT notice and mixer release test checking the exact upstream text are in mixer commit `41e9f34`; the audit also has a regression check for placeholder-only notices. New release artifacts are required before they are distributed. This crate appears in the `normal,build` trees for all six mixer release targets.

### Additional license-family review leads

- `ring` 0.17.14 declares `Apache-2.0 AND ISC`; the Last.fm v0.2.4 bundle includes its root `LICENSE`, `LICENSE-BoringSSL`, `LICENSE-other-bits` and nested third-party license files. Both sides of an `AND` expression and any embedded third-party notices need consideration; file presence alone does not establish that all obligations are satisfied.
- Mixer v0.11.6 inventories `encoding_rs` 0.8.35 as `(Apache-2.0 OR MIT) AND BSD-3-Clause`. Its included `COPYRIGHT` identifies the separate WHATWG-derived data and its `LICENSE-WHATWG`; the inventory and bundle also include both alternative code licenses. The notice bundle therefore explicitly carries the identified code and data notices, not merely one branch of the SPDX expression.
- All five inventories include `libsqlite3-sys` with the rusqlite MIT license; the vendored source also contains the SQLite amalgamation. This is a distinct embedded upstream component, so the MIT wrapper notice alone should not be presented as an attribution or license review of every SQLite source file. The [SQLite project states](https://www.sqlite.org/copyright.html) that its deliverable library code is dedicated to the public domain, while some build scripts may have other terms. The full amalgamation is present in the corresponding source; this statement is not an independent review of every file or jurisdiction.
- `webpki-roots` declares `CDLA-Permissive-2.0`; its license text is present in the Last.fm notice bundle. The [CDLA text](https://cdla.dev/permissive-2-0/) requires making the agreement available when sharing covered data; whether and how the conditions apply to a particular binary and its certificate material remains a substantive review point.
- ICU-related crates and `unicode-ident` include `Unicode-3.0` in their declarations. The [Unicode License v3](https://spdx.org/licenses/Unicode-3.0.html) requires preserving the specified notice in copies or associated documentation; inspect the exact bundled text and relevant target graphs rather than treating an SPDX expression as the notice itself.
- A package expression using `OR` may offer a choice of license, whereas `AND` combines obligations. The inventory is not a record of which alternative was selected or a complete legal compatibility analysis.

### Offline build check

The published Library Signals v0.3.2, Last.fm v0.2.4, learner v0.1.2, optimizer v0.2.7 and mixer v0.11.6 source archives were independently unpacked to isolated temporary directories and built on Windows with separate empty `CARGO_HOME` directories using `cargo build --locked --offline -j 1`. The provider executables reported their expected versions and SPI v2, the optimizer reported v0.2.7, and the learner and mixer displayed their help; the latter identified itself as v0.11.6. The mixer build emitted a linker-output warning and a Rust future-incompatibility warning for `net2` 0.2.39. These are debug-profile builds on one host, not cross-platform or bit-identical release rebuilds.

Run Cargo from the extracted archive's `source` directory: its `.cargo/config.toml` selects the vendored dependencies. A test invoking Cargo from outside that directory using only `--manifest-path` did not load that config and could not fetch the Git dependency in offline mode. This is a Cargo configuration-discovery constraint, not a missing vendor dependency. All five source-archive generators and their tests now explicitly include this instruction in new commits; already published archives retain their earlier wording.

### Release build inputs to verify

- The mixer v0.11.6 release workflow rewrites its checked-in Bullseye Dockerfiles to Debian Bookworm before the Linux builds. The learner v0.1.2 release workflow does **not** perform that rewrite: it builds its checked-in Bullseye Dockerfiles directly. Both sets of Dockerfiles install system packages, download `rustup` and install a default Rust toolchain inside the image. Mixer v0.11.6 also has a project `rust-toolchain.toml` selecting 1.97.1; learner v0.1.2 has no such file. In particular, the learner workflow's separate pinned Rust toolchain step for tests, macOS and Windows does not pin the Linux container's default toolchain. Record actual toolchain and image/package versions or pin them when reproducible release builds are required.
- The current learner Linux Docker build scripts invoke `cargo build --release` without `--locked`; the mixer's scripts include `--locked`. The source snapshot has a lockfile, but the learner command does not enforce it. Check and harden the release build separately before relying on the lockfile as an invariant.
- Follow-up learner commit `f7ec135` makes both Dockerfiles explicitly install Rust 1.97.1 and its x86/ARM build scripts invoke Cargo with `--locked`. Regression tests exercise both build scripts and check both image configurations. These changes are not in v0.1.2 or a published release, and have not yet been validated in an actual Linux container or cross-build. Debian package versions and other environment inputs remain unpinned.
- The optimizer and both native guidance providers use a checksum-verified `cross` v0.2.5 executable for ARM builds. Its build images, system libraries and platform toolchains are additional environment inputs, not Cargo-vendored crates. Windows and macOS builds likewise depend on the runner's toolchains and platform SDKs. Identify versions and relevant redistribution obligations for materials actually shipped; a build dependency is not automatically a component of the output.

These are build-input and reproducibility leads, not findings that a particular tool or system library must be redistributed under GPLv3. The source archives and package checks alone do not establish the exact complete environment for every historical binary.

## Findings and mitigations

The following records the issues as identified during review. Later bullets and the verification section describe mitigations; historical releases remain outside the requested remediation scope.

- The source-archive generator in the supplied overlay was **not adopted**. It resolves a mutable native release tag at packaging time but does not establish that this commit was the one that produced the published binaries. It also rewrites Cargo configuration, does not prove a successful offline rebuild on each platform, and does not establish that all applicable notices and non-Cargo build inputs are present. A vendored source tree alone is not evidence of complete Corresponding Source.
- The modified plugin workflows include a license, preliminary component notices, a plugin-source ZIP from the workflow commit, and a provenance file containing the plugin commit and selected native release tag(s). They now require a checksummed source snapshot whose manifest commit matches the selected native tag and link to it from the package. The native workflows propose a vendored source snapshot from the same workflow commit. This is **not yet** demonstrated to be a complete Corresponding Source mechanism: build instructions, third-party notices, distribution availability and the actual native binary provenance need further review. In particular, a matching source archive and tag are not proof that previously published binaries were built from that commit.
- Concrete historical mismatch: [`bliss-mixer` v0.11.5](https://github.com/chrober/bliss-mixer/releases/tag/v0.11.5) resolves to tag commit `5f2430aae765521f71cb6cae47c90c7d3eff1fcc`, but its release notes and [successful workflow 38932735412](https://github.com/chrober/bliss-mixer/actions/runs/38932735412) identify build commit `0a803def0bfc48afb78f7508c622e23676e1019a`. Those commits differ in `.github/workflows/release.yml`. Source based solely on the tag would therefore omit the actual build-workflow changes. Determine and preserve the exact release inputs rather than silently relabeling either commit.
- The component notices are preliminary. Generate and review an inventory of the resolved dependency graph for every released native component, retaining applicable copyright, license and NOTICE material; confirm handling of build-time and statically linked dependencies. Do not characterize the current notes as a complete third-party inventory.
- The notice gap is concrete, not merely a missing metadata field: the mixer's Windows normal-dependency tree includes `alloc-stdlib` 0.2.2. Its published crate omits a root license file, while the [upstream license at the crate's recorded source commit](https://github.com/dropbox/rust-alloc-no-stdlib/blob/6032b6a9b20e03737135c55a0270ccffcc1438ef/LICENSE) requires its copyright notice, conditions and disclaimer to accompany binary redistributions. The current preliminary Lab notice does not contain them. The same dependency tree includes `convert_case` 0.4.0, `fxhash` 0.2.1, `kernel32-sys` 0.2.2 and `ws2_32-sys` 0.2.1, whose downloaded crates also have no root license file; inspect their applicable source and attribution rather than inventing text. Package the reviewed material alongside the native binaries and in consuming plugin packages, and cover all supported target graphs before removing the preliminary designation.
- The optimizer's normal-dependency trees include `uuid-simd` 0.8.0 and `vsimd` 0.8.0 for each checked target. Their crate packages omit root license files; their recorded source commit contains the [upstream MIT license](https://github.com/Nugine/simd/blob/d74c030d9dc4f3cae02146d1f497ff62726ef09a/LICENSE). Preserve the original notice and permission text in the appropriate source and binary distribution material. Presence of an SPDX expression alone does not supply the missing copyright text.
- A 2026-11-01 `cargo tree --locked --edges normal` check against Linux x86/ARM, macOS x86/ARM and Windows x86 target triples found the optimizer pair above on every checked target, and `alloc-stdlib`, `convert_case` and `fxhash` on each mixer target; Windows additionally included `kernel32-sys` and `ws2_32-sys`. No missing root license file was detected by the same heuristic in the three other native components' normal dependency trees. This is triage, not a complete license audit: feature selection, build-time material, nested files and special license obligations still need review.
- Follow-up changes add the identified upstream license texts as supplemental native release assets and arrange for the two consuming plugin ZIPs to include them. The `convert_case` MIT license was added by its author in a descendant of the crate's recorded source commit; the legacy WinAPI notice is from an upstream historical revision and matches the crate source headers. Each native workflow now also builds a separate, checksummed ZIP containing the vendored license/notice files and dependency manifest; each consuming plugin workflow checks and includes the appropriate ZIP. Collection includes `AUTHORS` files, and refuses linked notices. Local unit tests and package staging tests passed against synthetic inputs and actual earlier source artifacts. [Last.fm](https://github.com/chrober/bliss-guidance-lastfm/actions/runs/41283411661), [Library Signals](https://github.com/chrober/bliss-guidance-library-signals/actions/runs/41283413886), [optimizer](https://github.com/chrober/bliss-playlist-optimizer/actions/runs/41283416042), [mixer](https://github.com/chrober/bliss-mixer/actions/runs/41283417837) and [learner](https://github.com/chrober/bliss-learner/actions/runs/41283419850) dry runs verify an earlier version of the bundle jobs; subsequent updates require another verification. These supplements cover the identified gaps only; the notices remain preliminary until remaining dependencies and obligations are reviewed.
- Separately published native binaries also require a version-specific source-availability solution. The owner has deferred review of existing development snapshots; this work targets future releases.

## Overlay review

The supplied archive contained full GPLv3 texts, replacement READMEs, four copies of source/notice packaging scripts and a workflow patcher. The license texts were retained where appropriate, but the overlay was not extracted over the repositories. Existing local README edits were preserved. The patcher uses textual anchors and may make partial modifications before reporting an error; it has no demonstrated idempotence or compatibility tests against these local workflows. Its generated corresponding-source claims were not accepted without verification.

The local changes to the four plugin workflows copy the repository license and preliminary notices into each platform package, record the effective plugin commit and native release inputs, generate a separate plugin source ZIP, and check those packaged files. The Last.fm workflow additionally checks the downloaded native binary checksums. Five native release workflows now have a proposed source job that snapshots their Git commit, vendors locked Cargo dependencies, and publishes that snapshot and a checksum with the native binaries. All nine workflows reject publishing against an existing tag that resolves to a different build commit, even when no GitHub Release exists yet. These changes are packaging improvements, not evidence of complete GPL compliance.

## Follow-up verification

- Verify each new native release's tag, build commit, source manifest and published checksums, as well as the consuming plugin packages and feed entries.
- Keep the per-dependency license inventory and supplemental notices current when Cargo dependencies change. Presence checks do not replace a substantive review of license obligations, particularly where the exact historical upstream license revision is uncertain.
- The Windows offline source builds are limited to the components and profiles identified above. Cross-platform offline rebuilds and independent legal review remain additional assurance, not results established by the package tests.

GPLv3's source-conveyance conditions are described in [section 6 of the license](https://www.gnu.org/licenses/gpl-3.0.html) and the [GNU GPL FAQ](https://www.gnu.org/licenses/gpl-faq.en.html). Specific legal conclusions should be reviewed with appropriate counsel.
